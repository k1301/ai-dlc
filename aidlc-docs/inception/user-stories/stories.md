# Part A: Customer Journey Stories

## Story 1: 테이블 태블릿 자동 로그인 및 세션 시작

**Priority**: Critical (MVP)

**User Story**:
매장 고객으로서, 테이블에 앉자마자 별도의 로그인 절차 없이 자동으로 메뉴 화면을 볼 수 있어야 한다. 그래야 대기 시간 없이 즉시 주문을 시작할 수 있다.

**Description**:
고객이 테이블에 착석하면 테이블 태블릿은 이미 해당 테이블로 로그인되어 있어야 하며, 자동으로 메뉴 화면이 표시되어야 한다. 관리자가 사전에 1회 초기 설정(매장 식별자, 테이블 번호, 테이블 비밀번호)을 완료한 상태이며, 이후 모든 고객은 별도의 로그인 없이 바로 메뉴를 볼 수 있다.

**Acceptance Criteria**:
- **Given**: 관리자가 테이블 태블릿의 초기 설정을 완료한 상태
- **When**: 고객이 테이블 태블릿을 확인
- **Then**: 자동으로 메뉴 화면이 표시되어야 함 (로그인 화면 없음)

- **Given**: 테이블 태블릿이 이미 로그인되어 있는 상태
- **When**: 페이지를 새로고침하거나 브라우저를 다시 열 때
- **Then**: 저장된 로그인 정보로 자동 로그인되어 메뉴 화면이 표시되어야 함

**Related Requirements**: FR-1.1

**INVEST Check**:
- ✅ Independent: 다른 스토리와 독립적
- ✅ Negotiable: 자동 로그인 방식은 협상 가능
- ✅ Valuable: 고객에게 즉시 주문 시작 가능한 가치 제공
- ✅ Estimable: 개발 노력 추정 가능
- ✅ Small: 한 스프린트 내 완료 가능
- ✅ Testable: 자동 로그인 여부로 테스트 가능

## Story 2: 메뉴 탐색 및 선택

**Priority**: Critical (MVP)

**User Story**:
매장 고객으로서, 카테고리별로 정리된 메뉴를 쉽게 탐색하고 각 메뉴의 이미지와 설명을 확인할 수 있어야 한다. 그래야 원하는 메뉴를 빠르게 찾아 선택할 수 있다.

**Description**:
메뉴 화면은 테이블 태블릿의 기본 화면이며, 고객은 카테고리(예: 메인 요리, 음료, 디저트)별로 메뉴를 탐색할 수 있다. 각 메뉴는 카드 형태로 표시되며, 메뉴명, 가격, 설명, 이미지를 포함한다. 터치 친화적인 인터페이스로 카테고리 간 빠른 이동이 가능하다.

**Acceptance Criteria**:
- **Given**: 고객이 메뉴 화면에 있음
- **When**: 카테고리를 선택할 때
- **Then**: 해당 카테고리의 메뉴 목록이 카드 형태로 표시되어야 함

- **Given**: 메뉴 카드가 표시된 상태
- **When**: 메뉴 카드를 클릭할 때
- **Then**: 메뉴의 상세 정보(이미지, 설명, 가격)가 표시되어야 함

**Related Requirements**: FR-1.2

**INVEST Check**:
- ✅ Independent: 로그인 이후 독립적으로 동작
- ✅ Negotiable: 레이아웃과 카테고리 구조는 협상 가능
- ✅ Valuable: 고객이 원하는 메뉴를 쉽게 찾는 가치 제공
- ✅ Estimable: 개발 노력 추정 가능
- ✅ Small: 한 스프린트 내 완료 가능
- ✅ Testable: 카테고리 탐색 및 메뉴 표시로 테스트 가능

## Story 3: 장바구니 관리

**Priority**: Critical (MVP)

**User Story**:
매장 고객으로서, 선택한 메뉴를 장바구니에 추가하고 수량을 조절하며 총 금액을 실시간으로 확인할 수 있어야 한다. 그래야 주문 전에 내가 선택한 메뉴와 금액을 검토하고 조정할 수 있다.

**Description**:
고객은 메뉴를 선택하면 장바구니에 추가할 수 있으며, 장바구니에서 메뉴 수량을 증가/감소시키거나 삭제할 수 있다. 총 주문 금액은 실시간으로 계산되어 표시된다. 장바구니 내용은 클라이언트 측에 저장되어 페이지 새로고침 시에도 유지된다.

**Acceptance Criteria**:
- **Given**: 고객이 메뉴를 선택한 상태
- **When**: "장바구니에 추가" 버튼을 클릭할 때
- **Then**: 해당 메뉴가 장바구니에 추가되고 총 금액이 업데이트되어야 함

- **Given**: 장바구니에 메뉴가 있는 상태
- **When**: 수량을 증가/감소시키거나 메뉴를 삭제할 때
- **Then**: 총 금액이 실시간으로 재계산되어야 함

**Related Requirements**: FR-1.3

**INVEST Check**:
- ✅ Independent: 메뉴 조회 후 독립적으로 동작
- ✅ Negotiable: 장바구니 UI는 협상 가능
- ✅ Valuable: 고객이 주문 전에 검토 및 수정 가능한 가치 제공
- ✅ Estimable: 개발 노력 추정 가능
- ✅ Small: 한 스프린트 내 완료 가능
- ✅ Testable: 장바구니 추가/수정/삭제로 테스트 가능

## Story 4: 주문 생성 및 확정

**Priority**: Critical (MVP)

**User Story**:
매장 고객으로서, 장바구니의 메뉴를 최종 확인하고 주문을 확정할 수 있어야 한다. 주문 성공 시 주문 번호를 확인하고 자동으로 메뉴 화면으로 돌아가야 한다. 그래야 추가 주문을 쉽게 할 수 있다.

**Description**:
고객은 장바구니에서 주문 내역을 최종 확인한 후 "주문 확정" 버튼을 클릭하여 주문을 생성한다. 주문 성공 시 주문 번호가 표시되고, 장바구니는 자동으로 비워지며, 메뉴 화면으로 자동 리다이렉트된다. 주문 실패 시 에러 메시지가 표시되고 장바구니는 유지된다.

**Acceptance Criteria**:
- **Given**: 장바구니에 메뉴가 있는 상태
- **When**: "주문 확정" 버튼을 클릭하고 주문이 성공할 때
- **Then**: 주문 번호가 표시되고, 장바구니가 비워지며, 메뉴 화면으로 자동 리다이렉트되어야 함

- **Given**: 장바구니에 메뉴가 있는 상태
- **When**: "주문 확정" 버튼을 클릭했으나 주문이 실패할 때
- **Then**: 에러 메시지가 표시되고 장바구니는 유지되어야 함

**Related Requirements**: FR-1.4

**INVEST Check**:
- ✅ Independent: 장바구니 관리 후 독립적으로 동작
- ✅ Negotiable: 주문 확정 플로우는 협상 가능
- ✅ Valuable: 고객이 주문을 완료하는 핵심 가치 제공
- ✅ Estimable: 개발 노력 추정 가능
- ✅ Small: 한 스프린트 내 완료 가능
- ✅ Testable: 주문 성공/실패 시나리오로 테스트 가능

## Story 5: 주문 내역 조회

**Priority**: High (MVP)

**User Story**:
매장 고객으로서, 내가 주문한 메뉴의 내역을 확인하고 주문 상태(대기중/준비중/완료)를 볼 수 있어야 한다. 그래야 내가 무엇을 주문했는지 기억하고 주문 진행 상황을 파악할 수 있다.

**Description**:
고객은 "주문 내역" 버튼을 통해 현재 테이블 세션의 모든 주문을 시간 순으로 조회할 수 있다. 각 주문은 주문 번호, 주문 시각, 메뉴 목록, 수량, 총 금액, 주문 상태를 표시한다. 이전 세션의 주문(매장 이용 완료 처리된 주문)은 표시되지 않는다.

**Acceptance Criteria**:
- **Given**: 고객이 하나 이상의 주문을 생성한 상태
- **When**: "주문 내역" 버튼을 클릭할 때
- **Then**: 현재 세션의 모든 주문이 시간 순으로 표시되어야 하며, 각 주문의 상세 정보(주문 번호, 시각, 메뉴, 금액, 상태)가 포함되어야 함

- **Given**: 주문 내역 화면에 있는 상태
- **When**: 관리자가 주문 상태를 변경할 때
- **Then**: 고객 화면의 주문 상태가 업데이트되어야 함 (optional: 실시간 업데이트)

**Related Requirements**: FR-1.5

**INVEST Check**:
- ✅ Independent: 주문 생성 후 독립적으로 동작
- ✅ Negotiable: 주문 내역 표시 방식은 협상 가능
- ✅ Valuable: 고객이 자신의 주문을 추적하는 가치 제공
- ✅ Estimable: 개발 노력 추정 가능
- ✅ Small: 한 스프린트 내 완료 가능
- ✅ Testable: 주문 내역 조회 및 표시로 테스트 가능

# Part B: Admin Journey Stories

## Story 6: 관리자 로그인 및 인증

**Priority**: Critical (MVP)

**User Story**:
매장 관리자로서, 매장 식별자와 사용자명/비밀번호를 사용하여 관리 시스템에 로그인하고 16시간 동안 세션을 유지할 수 있어야 한다. 그래야 매장 운영 중 지속적으로 주문을 관리할 수 있다.

**Description**:
관리자는 매장 식별자, 사용자명, 비밀번호를 입력하여 로그인한다. 로그인 성공 시 JWT 토큰이 발급되며 16시간 동안 세션이 유지된다. 브라우저 새로고침 시에도 세션이 유지되며, 16시간 후 자동으로 로그아웃된다. 비밀번호는 bcrypt로 해싱되어 저장되며, 로그인 시도 제한이 적용된다.

**Acceptance Criteria**:
- **Given**: 관리자가 로그인 화면에 있음
- **When**: 올바른 매장 식별자, 사용자명, 비밀번호를 입력하고 로그인 버튼을 클릭할 때
- **Then**: JWT 토큰이 발급되고 관리자 대시보드로 리다이렉트되어야 함

- **Given**: 관리자가 로그인된 상태에서 브라우저를 새로고침할 때
- **When**: 페이지가 다시 로드될 때
- **Then**: 세션이 유지되어 로그인 상태가 유지되어야 함

**Related Requirements**: FR-2.1

**INVEST Check**:
- ✅ Independent: 다른 스토리와 독립적
- ✅ Negotiable: 인증 방식은 협상 가능
- ✅ Valuable: 관리자가 시스템에 접근하는 기본 가치 제공
- ✅ Estimable: 개발 노력 추정 가능
- ✅ Small: 한 스프린트 내 완료 가능
- ✅ Testable: 로그인 성공/실패로 테스트 가능

## Story 7: 실시간 주문 모니터링

**Priority**: Critical (MVP)

**User Story**:
매장 관리자로서, 모든 테이블의 주문을 실시간으로 모니터링하고 테이블별 총 주문액과 최신 주문을 한눈에 파악할 수 있어야 한다. 그래야 신속하게 주문에 대응하고 매장을 효율적으로 운영할 수 있다.

**Description**:
관리자 대시보드는 그리드 형태로 테이블별 카드를 표시한다. 각 카드에는 테이블 번호, 총 주문액, 최신 주문 n개가 미리보기로 표시된다. 새 주문이 들어오면 Server-Sent Events(SSE)를 통해 2초 이내에 화면에 표시되며, 시각적 강조(색상 변경, 애니메이션)로 알려준다. 주문 카드를 클릭하면 해당 테이블의 전체 주문 목록이 상세하게 표시된다.

**Acceptance Criteria**:
- **Given**: 관리자가 대시보드에 로그인한 상태
- **When**: 고객이 주문을 생성할 때
- **Then**: 2초 이내에 해당 테이블 카드에 새 주문이 표시되고 시각적으로 강조되어야 함

- **Given**: 대시보드에 테이블 카드가 표시된 상태
- **When**: 테이블 카드를 클릭할 때
- **Then**: 해당 테이블의 전체 주문 목록(주문 번호, 시각, 메뉴, 금액, 상태)이 상세하게 표시되어야 함

**Related Requirements**: FR-2.2

**INVEST Check**:
- ✅ Independent: 로그인 후 독립적으로 동작
- ✅ Negotiable: 대시보드 레이아웃은 협상 가능
- ✅ Valuable: 관리자가 주문을 실시간으로 파악하는 핵심 가치 제공
- ✅ Estimable: 개발 노력 추정 가능
- ✅ Small: SSE 구현 포함하여 한 스프린트 내 완료 가능
- ✅ Testable: 실시간 주문 표시 및 업데이트로 테스트 가능

## Story 8: 주문 상태 관리 및 삭제

**Priority**: Critical (MVP)

**User Story**:
매장 관리자로서, 주문 상태를 변경(대기중/준비중/완료)하고 필요시 잘못된 주문을 삭제할 수 있어야 한다. 그래야 주문 진행 상황을 추적하고 실수를 수정할 수 있다.

**Description**:
관리자는 각 주문의 상태를 "대기중", "준비중", "완료"로 변경할 수 있다. 잘못된 주문을 삭제할 때는 확인 팝업이 표시되며, 삭제 시 해당 테이블의 총 주문액이 재계산된다. 모든 작업 후 성공/실패 피드백이 제공된다.

**Acceptance Criteria**:
- **Given**: 관리자가 주문 목록을 보고 있는 상태
- **When**: 주문의 상태를 변경할 때
- **Then**: 주문 상태가 즉시 업데이트되고 성공 메시지가 표시되어야 함

- **Given**: 관리자가 주문 삭제 버튼을 클릭한 상태
- **When**: 확인 팝업에서 "삭제"를 선택할 때
- **Then**: 주문이 삭제되고, 테이블 총 주문액이 재계산되며, 성공 메시지가 표시되어야 함

**Related Requirements**: FR-2.3 (일부)

**INVEST Check**:
- ✅ Independent: 주문 모니터링 후 독립적으로 동작
- ✅ Negotiable: 상태 변경 UI는 협상 가능
- ✅ Valuable: 관리자가 주문을 제어하는 가치 제공
- ✅ Estimable: 개발 노력 추정 가능
- ✅ Small: 한 스프린트 내 완료 가능
- ✅ Testable: 상태 변경 및 삭제로 테스트 가능

## Story 9: 테이블 세션 관리

**Priority**: Critical (MVP)

**User Story**:
매장 관리자로서, 테이블 세션을 종료(매장 이용 완료)하고 새 고객을 위해 테이블을 초기화할 수 있어야 한다. 또한 과거 주문 내역을 조회할 수 있어야 한다. 그래야 테이블을 효율적으로 회전시키고 필요시 이전 주문 기록을 확인할 수 있다.

**Description**:
관리자는 고객이 식사를 마치면 "테이블 이용 완료" 버튼을 클릭하여 해당 테이블 세션을 종료한다. 확인 팝업 후 세션이 종료되면 해당 세션의 주문 내역은 과거 이력으로 이동하고, 테이블의 현재 주문 목록과 총 주문액은 0으로 리셋된다. "과거 내역" 버튼을 통해 테이블별 과거 주문을 날짜 필터링하여 조회할 수 있다.

**Acceptance Criteria**:
- **Given**: 관리자가 활성 테이블의 "이용 완료" 버튼을 클릭한 상태
- **When**: 확인 팝업에서 "완료"를 선택할 때
- **Then**: 테이블 세션이 종료되고, 주문 내역이 과거 이력으로 이동하며, 테이블 현재 주문이 0으로 리셋되어야 함

- **Given**: 관리자가 "과거 내역" 버튼을 클릭한 상태
- **When**: 특정 테이블을 선택하고 날짜 범위를 설정할 때
- **Then**: 해당 테이블의 과거 주문 목록(주문 번호, 시각, 메뉴, 금액, 완료 시각)이 표시되어야 함

**Related Requirements**: FR-2.3

**INVEST Check**:
- ✅ Independent: 주문 모니터링 후 독립적으로 동작
- ✅ Negotiable: 세션 종료 플로우는 협상 가능
- ✅ Valuable: 관리자가 테이블을 회전시키는 가치 제공
- ✅ Estimable: 개발 노력 추정 가능
- ✅ Small: 한 스프린트 내 완료 가능
- ✅ Testable: 세션 종료 및 과거 내역 조회로 테스트 가능

## Story 10: 메뉴 관리

**Priority**: High (MVP)

**User Story**:
매장 관리자로서, 메뉴를 추가, 수정, 삭제하고 카테고리별로 조회할 수 있어야 한다. 그래야 메뉴 변경 시 즉시 시스템에 반영하여 고객에게 최신 메뉴를 제공할 수 있다.

**Description**:
관리자는 메뉴 관리 화면에서 카테고리별로 메뉴를 조회할 수 있다. 새 메뉴를 등록할 때는 메뉴명, 가격, 설명, 카테고리, 이미지 URL을 입력한다. 기존 메뉴를 수정하거나 삭제할 수 있으며, 메뉴 노출 순서를 조정할 수 있다. 필수 필드 검증과 가격 범위 검증이 적용된다.

**Acceptance Criteria**:
- **Given**: 관리자가 메뉴 관리 화면에 있음
- **When**: 새 메뉴 정보(메뉴명, 가격, 설명, 카테고리, 이미지 URL)를 입력하고 "등록" 버튼을 클릭할 때
- **Then**: 메뉴가 등록되고 메뉴 목록에 표시되어야 하며, 고객 화면에도 즉시 반영되어야 함

- **Given**: 관리자가 메뉴 목록을 보고 있는 상태
- **When**: 메뉴를 수정하거나 삭제할 때
- **Then**: 변경 사항이 즉시 저장되고 고객 화면에 반영되어야 함

**Related Requirements**: FR-2.4

**INVEST Check**:
- ✅ Independent: 다른 스토리와 독립적
- ✅ Negotiable: 메뉴 관리 UI는 협상 가능
- ✅ Valuable: 관리자가 메뉴를 동적으로 관리하는 가치 제공
- ✅ Estimable: 개발 노력 추정 가능
- ✅ Small: 한 스프린트 내 완료 가능
- ✅ Testable: 메뉴 CRUD 작업으로 테스트 가능

## Story 11: 테이블 태블릿 초기 설정

**Priority**: High (MVP)

**User Story**:
매장 관리자로서, 새 테이블 태블릿을 초기 설정(테이블 번호, 테이블 비밀번호)하여 자동 로그인을 활성화할 수 있어야 한다. 그래야 고객이 별도 로그인 없이 즉시 주문할 수 있도록 준비할 수 있다.

**Description**:
관리자는 테이블 태블릿에서 초기 설정 화면을 통해 매장 식별자, 테이블 번호, 테이블 비밀번호를 입력한다. 설정이 완료되면 16시간 세션이 생성되고, 설정 정보가 로컬에 저장되어 이후 자동 로그인이 활성화된다.

**Acceptance Criteria**:
- **Given**: 관리자가 새 테이블 태블릿의 초기 설정 화면에 있음
- **When**: 매장 식별자, 테이블 번호, 테이블 비밀번호를 입력하고 "설정 완료" 버튼을 클릭할 때
- **Then**: 설정이 저장되고, 자동으로 메뉴 화면으로 이동하며, 이후 자동 로그인이 활성화되어야 함

**Related Requirements**: FR-2.3 (일부), FR-1.1 (연계)

**INVEST Check**:
- ✅ Independent: 다른 스토리와 독립적
- ✅ Negotiable: 초기 설정 UI는 협상 가능
- ✅ Valuable: 테이블 태블릿을 사용 가능하도록 준비하는 가치 제공
- ✅ Estimable: 개발 노력 추정 가능
- ✅ Small: 한 스프린트 내 완료 가능
- ✅ Testable: 초기 설정 및 자동 로그인 활성화로 테스트 가능
